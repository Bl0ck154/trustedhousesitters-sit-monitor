# TrustedHousesitters Sit Monitor

Unofficial self-hosted personal-use monitor for publicly accessible house-sitting listings. It is not affiliated with, endorsed by or operated by TrustedHousesitters.

## What it does

- Finds house sits within a rolling date window and filters by country, pet type, transport and Wi-Fi.
- Reads embedded JSON in public HTML via HTTPS, without a browser by default. Full scan every 30 minutes plus a quick new-listing lane every 5 minutes.
- Uses SQLite history and a 30-minute detail cache for unchanged open listings.
- Revalidates listings before alerting, independently tracks status changes and deduplicates announcements.
- Opens detail pages only for Open, cat-only candidates without explicit negative transport/Wi-Fi flags. Search summaries often omit Wi-Fi and transport, so missing fields are verified on the detail page rather than treated as rejection. Other sits remain search-state observations only.
- Sends Telegram photo cards, detailed formatted descriptions, native photo albums, and approximate-location links.
- Allows manually marking applications. These markers are not synchronized with a TrustedHousesitters account.

## Running

Requires Python 3.10+, a personal Telegram bot, and network access to the site's public pages. Clone the repository and configure the runtime in its private data directory.

Example environment variables:

    THS_EARLIEST_START=2026-11-01
    THS_FETCH_MODE=http

Create data/config.env with these variables; this file is never committed. To pair Telegram, run setup_telegram.py with Python 3 and follow its instructions. Never share or commit the bot token.

Use run-hourly.sh for full scans, run-quick.sh for incremental new-listing scans, run-telegram.sh for delivery, and telegram_fast_callbacks.py as a persistent restricted service for Telegram button presses. A 30-minute full scan, 5-minute quick scan and 5-minute Telegram delivery interval are suitable moderate configurations. Adapt the host-specific cron/systemd paths to your machine. If you want to diagnose the browser fallback, install Obscura Lite and set THS_FETCH_MODE=browser, adjusting the local path in monitor.py.

Run tests with:

    python3 -m unittest discover -p 'test_*.py'

## Privacy and limits

Collected listings, owner descriptions, photos' source URLs, private application flags, Telegram IDs, bot credentials, and notification history are stored under data/ locally and ignored by Git. Do not publish any collected data, logs, browser sessions or secrets.

The HTML structure and access policies can change. Respect the platform's terms, robots rules, rate limits and access restrictions; do not bypass authentication or anti-abuse controls. A non-200 HTTP response is treated as a failed fetch, not something to evade. This is not a supported or official API, and public search cannot confirm a personal Apply button or personal application status.

No license is included; public visibility is not a grant of reuse rights.


## Trip-first search and manual confirmations

The monitor prioritizes **finding housing**, not merely one species. The default is:
- A: cats, rabbits, hamsters, guinea pigs and other small home pets; full-detail verification and immediate relevant alerts.
- B: one or two dogs, possibly alongside cats/small pets; prefetch and show under `/options` before urgency, then alert as the next uncovered date approaches (within nine days).
- C: farm/horse/complex multi-animal sits; usually skipped.

The planner searches from the private earliest-start configuration. A confirmed stay is recorded **only** when the sitter explicitly marks their own booking through `/confirm ID` or the Telegram card's two-step confirmation button. The site's public Confirmed/Reviewing label does not establish that the sitter was accepted. Confirmed dates are blocked from new recommendations. If a brief uncovered gap remains before a booking, `/plan` reports the bridging nights while the next normal-length sit search can advance past the confirmed departure.

Telegram commands: `/applications`, `/plan`, `/options`, `/report`, `/talking ID`, `/confirm ID`, `/reject ID`, `/applied ID`, `/withdraw ID`. Application stages are private to the local SQLite database.

A local 08:30 morning summary is generated by `telegram_daily.py` and `run-daily.sh`, when added to the sitter's local cron. It runs at most once per day and does not require ChatGPT automations. Run `python3 telegram_daily.py --dry-run --force` to preview. Schedule the shell wrapper with a local 08:30 cron entry if the machine shares the sitter's timezone.

Beware that HTTP access to the public site may change, and no personal booking status is fetched without user action.


## Time-critical openings and reopenings

The production layout can use three **independent, serialized lanes**, rather than one slow dispatcher:

- New public Open sits: `run-quick.sh` every **2 minutes**, checking 3 pages sorted by publication date; the full catalog is still swept every **30 minutes** to catch omissions.
- New Telegram listing-card delivery: `run-telegram.sh` every **1 minute**, using `--delivery-only` so no lifecycle polling delays a new alert.
- Status watch of previously delivered assignments: `run-status.sh` every **2 minutes**, using `--status-only` and a separate `status.lock`. Recently changed (last 24 h) and Reviewing sits are verified at most every 2 minutes; other tracked sits every 4 minutes.

When a specific sit switches from Open to Reviewing, send a prompt plain-text alert with a clickable link and the observed application count. Reviewing does **not** mean the sitter has been selected; it means new applications are currently paused. When the exact assignment returns to Open, send a fresh **plain-text reopening alert** immediately after verification, without downloading photos again. Unchanged states do not generate repeated messages, and removal of dates still requires two independent observations. Unknown/failed page fetches cannot be treated as closure.

A definitive Telegram send failure leaves the old status intact for a later retry; an ambiguous network timeout may result in a duplicate rather than a silently missed important update. Intervals are approximate and cannot guarantee notification before applications fill up, especially if external network access is slow or rate-limited.

### Example personal cron configuration

    */30 * * * * /bin/bash /path/to/run-hourly.sh
    1-59/2 * * * * /bin/bash /path/to/run-quick.sh
    * * * * * /bin/bash /path/to/run-telegram.sh
    */2 * * * * /bin/bash /path/to/run-status.sh

Runtime state (logs, tokens, chat ID, applications) remains under ignored `data/`.


## Threaded status notifications and safe network fallback

All status-change messages (Reviewing, reopened Open, Confirmed or Removed)
reply directly to the **active original photo card**, not to another status
message. This works for migrated cards as well: those were edited to contain
the photo, whereas their old album posts may have been deleted. If Telegram
definitively reports that the original message is unavailable, the important
notification is still sent without a reply.

The monitor defaults to direct HTTPS access to **public, unauthenticated**
listing pages. Optional environment variables:

- `THS_FETCH_MODE=http` — direct public HTTP requests (default).
- `THS_BROWSER_FALLBACK=1` — retry an ordinary network error or a public
  page whose structured-data format changed using Obscura Lite.
- `THS_PROXY_FALLBACK=1` — on transient network failure only, try the
  canonical local proxy broker at `http://127.0.0.1:20140` **if** its
  validated TrustedHousesitters target pool has working upstreams.

These flags belong in a private `data/config.env` file. No proxy passwords,
login cookies, personal accounts or session tokens are sent through public
proxies. HTTP 403, HTTP 429 and detected security challenges **must not**
trigger a proxy or browser fallback. Instead, a shared access cooldown pauses
network calls for 1 hour on 429 and 6 hours for 403/challenges. This avoids
hammering the site or attempting to circumvent restrictions. A registered
proxy target is not proof of a working upstream: the broker may have no
validated pool, in which case no proxy retry occurs.

The optional shared proxy broker is configured in a different, private
infrastructure repository. This public project does not include broker
credentials or dynamic proxy lists. All Cron launchers load the private
config file before starting.


## User choices and separate apartment/pet galleries

Telegram bot sends one photo card with inline controls; the Bot API does not support inline keyboards on a native media group (2–10 items per album). To avoid delaying time-critical announcements, the initial card remains one photo with caption and buttons, while full-resolution native albums are sent on demand.

The listing's primary `photos` array can include images also present under `pets[].photos`. Home images are filtered to exclude pet images. Some valid Cloudinary public IDs lack a `.jpeg` suffix: these extensionless IDs must remain eligible. Two separate buttons show **home photos** and **pet photos**; opening a gallery refreshes current public metadata rather than reusing stale photo URLs.

**Application state**: the `Я подав заявку` action is idempotent. It changes to an explicit cancel button and shows the separate `Мене підтвердили` action only when the application is marked. Manual confirmation validates that an application exists. Telegram edit API can stall or time out; edit timeouts are shortened and unconfirmed keyboard redraws are queued in SQLite for later retries without reverting the application state.

**Dismissal**: `Не цікаво` stores a private ignored assignment ID. Dismissed listings are omitted from future notifications, reopening checks, `/options` and daily suggestions, without muting other sits in the same city. The choice can be reversed with the same card's `Повернути в моніторинг` button. A sitter may additionally mark an application rejected independently.

**Old reply keyboard**: send a Telegram Bot API message with `ReplyKeyboardRemove` (the CLI option `telegram_upgrade.py --reset-keyboard` does this) to clear a stale bottom keyboard left from an earlier bot setup. This is distinct from the photo cards' inline controls.
